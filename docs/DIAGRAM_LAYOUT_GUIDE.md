# ArchMapで読みやすい図を作る

図作成エージェントが、ソース作成前と描画レビュー時に読む配置ガイド。構文の正本は [SYNTAX.md](SYNTAX.md)。以下は現行実装の特徴と、それを踏まえた作図上の指針であり、任意の図で最適配置を保証するものではない。

## レンダラーの特徴と作図への影響

| 実装の特徴 | エージェントの判断 |
| --- | --- |
| Mermaidで解析し、ArchMap独自のグリッド配置・直交配線で描く | Mermaid標準レンダラーのプレビューを最終確認に使わない。Dagre/ELKや曲線設定でArchMapの配線を制御できると考えない。 |
| 一般の自動配置は接続の向きから段を求める。循環は同じ強連結成分として扱う | 本流を一方向に読む構成を先に決める。循環を含む図は宣言順だけで直列になると期待しない。戻り線の意味は保持し、必要なら詳細図を分ける。 |
| 同じ段の要素の順序には宣言順が関与する | 関連する要素をまとめて宣言し、並列枝の順序を整える。効果は描画して判断し、宣言順だけで位置を保証しない。 |
| グリッド間隔は大きなノード・長い接続ラベル・接続数・グループの深さの影響を受ける | 長文を一枚のカードや接続に詰め込まない。ラベルは区別できる短い語にし、詳細は付属文書に残す。ひとつの長い説明が全体を疎にしていないか見る。 |
| 線は図形とラベルを避け、共有線分・交差・距離・折れ曲がりを評価して選ばれる | 迂回には衝突回避の理由がある。まず迂回先の障害物やラベル、密集した枝を調べる。単に線を短くするために接続の意味を変えない。 |
| 同じ軸の対向接続は直線候補になる。fork/joinも軸の合う枝の接続点を中央に保つ | 主経路の前後を同じ列（縦方向）または行（横方向）に近づける。枝すべてを一本の軸へ押し込まず、別の線との重なりも確認する。障害物があれば直線は保証されない。 |
| グループの個別directionは内部を独立した配置単位にする | 境界が必要なところだけグループ化する。外側LR・内側TBなどを候補にする。装飾のための多重入れ子は見出しと余白を増やす。 |
| いずれかのノードに手動atがあると、個別directionによるグループ配置より手動配置を優先する | 自動配置と方向の調整を先に試す。atを加えると他のグループも配置が変わり得るため、全体を再レビューする。 |
| 空のグリッド行・列は詰められる | atはピクセル座標ではない。大きな番号で空白を作ろうとしない。書式・適用対象は構文仕様を参照する。 |
| シーケンスは参加者宣言順、layersはグループ順が配置に関わる | シーケンスは会話の多い参加者を隣接させ、layersは意図する層順に宣言する。これらにatを使わない。 |
| グループの折りたたみは内部を隠し外部接続を枠に集約する | 全体図の情報量削減に使える。ただし接続先の詳細が必要なら展開図・詳細図も渡す。 |

実装確認先：[配置・配線](https://github.com/ai-org-labs/archmap-mermaid/blob/main/src/focused/layout.ts)、[描画](https://github.com/ai-org-labs/archmap-mermaid/blob/main/src/focused/render.ts)。数値の重みや細かい座標は内部実装として扱い、プロンプトへ固定しない。

## 図種ごとの初手

次は推奨する初期案であり、強制ルールではない。読み手の端末と図の目的に合わせて選ぶ。

- **システム構成**：利用者・入口・主要処理・保存先の流れをLRで試す。サービスごとに細かく囲むより、システム境界や責務境界を表す。技術の上下層を伝えたい場合はlayersを検討する。
- **アクティビティ**：TBで主経路を縦に置き、例外を脇へ、並列処理を横へ展開する。choiceの条件は短く、forkとjoinの対応を保つ。循環や合流を減らす目的で業務上の線を削除しない。
- **画面遷移**：主要な利用経路を軸にする。戻る操作・モーダル・画面内操作を区別する。大量の共通ナビゲーションは全体図と機能別詳細図を分けて表現し、省略を明示する。
- **シーケンス**：参加者を主要な呼び出し順に宣言し、やり取りの多い隣同士を近くに置く。Noteや深いフレームの入れ子で一場面が縦長になりすぎたら場面別に分ける。
- **ER**：主要な関連が読みやすいLR/TBを比較する。属性の長さと数も寸法に影響する。全体図で属性を省略したら明記し、完全な定義は詳細図に保つ。関係の向きを見栄えだけで反転しない。
- **ユースケース**：アクターと責務境界、主な操作を先に整理する。include/extendは配置用の線として使わない。複数システムは境界ごとに読めるか確認する。
- **モバイルで読む図**：横長の図をFitで極端に縮小するだけでは読めない。TBや詳細図への分割を候補にする。全体の把握と実際に読む拡大率の両方を確認する。

## 改善の順序

1. **意味を固定する**：ノードID、接続先、向き、条件、関係種別を控える。配置変更後に差分で確認する。
2. **自動配置から始める**：図種と全体方向を決め、主経路と並列枝の宣言順を整理する。
3. **問題を具体化する**：「読みにくい」だけでなく、対象の線・ラベルと、交差／共有線分／余分な曲がり／文字切れ／過大な余白を記録する。
4. **小さく比較する**：方向、宣言順、グループの粒度・内部方向、ラベルの長さを一つずつ変えて再描画する。意味を変えずに比較する。
5. **必要なときだけ配置補助を使う**：標準の不可視線や仕様にあるatは、ユーザーが許容する場合に限定する。不可視線は描かれなくても配置に影響するため循環に注意する。架空の可視ノード・接続で位置を調整しない。標準構文だけという指定ならatを追加しない。
6. **全体で採否を決める**：一本が短くなっても、別の重なり・文字切れ・誤読を増やした案は戻す。改善しない調整を繰り返さず、図の分割かレンダラーの問題として整理する。

## 完了時の確認

構文エラーがないことだけを完了条件にしない。全体表示と文字を読める倍率で、主経路、分岐・合流、境界をまたぐ線、戻り線、長いラベルを確認する。

APIが利用できるなら `renderMermaid` の `layout` を補助にできる。`edges[].points` から折れ曲がりと線分の重なり、`labelBox` と `nodes` / `groups` から衝突を調べられる。ただし端点での接触と意図しない重なりを区別し、幾何学的な値だけで読めると断定しない。

最終報告では、配置上の判断と残る問題を短く示す。例：「主経路を縦に、並列枝を横に整理。決済前後は直線。例外の戻り線は外周に残る」。ブラウザーで見ていない場合は、見た目の確認済みと書かない。
