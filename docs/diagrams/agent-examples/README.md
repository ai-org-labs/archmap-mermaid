# エージェント作図の試行

題材は架空のPDF解析サービス。要件確定済みの実システムではありません。同期処理の構成、非同期の処理手順、通信の流れを別の図として試しました。アクティビティは処理手順の抜粋、シーケンスはジョブ管理の更新を省略した通信例です。

[一覧を開く](index.html)

- [システム構成](01-pdf-system.svg) / [ソース](01-pdf-system.mmd)：全体TB・非同期処理LR。共有データを分離して比較。レンダラー改善後は交差0、折れ曲がり9。外周線は交差回避のために維持。
- [アクティビティ](02-pdf-activity.svg) / [ソース](02-pdf-activity.mmd)：主経路を縦に、並列処理と受付エラーを右へ。分岐・合流の中央は直線。高さを2276→1800へ縮小。例外終了線は本流との混同を避けて外周へ。
- [シーケンス](03-pdf-sequence.svg) / [ソース](03-pdf-sequence.mmd)：利用者→API→キュー→ワーカー→ストアの宣言順。活性区間・自己呼び出し・結果照会の条件分岐を確認。APIからストアへの線は長い。

## 実施した確認

- ローカルのArchMap `renderMermaid` をブラウザーから呼び出し、3図のエラー・警告がないことを確認。
- SVGとPNGを生成して目視確認。これはエージェント手順を使った作図の試行であり、Copilotなど各製品でのエージェント起動試験ではない。
- システム構成は、受付側にジョブ管理を含む初稿から、共有データを別枠にする案へ変更。ノード6個と接続7本は維持した。
- 共有データを分けたLR案は2490×320と横長になり、TB案1260×980を採用。曲がりの数だけで採否を決めなかった。
- アクティビティのchoiceは「受付可能？」へ短縮。条件は形式と容量の検査を意味する。並列バーは日本語の見出しにした。

## レンダラー改善後の再検証

| 対象 | 改善前 | 改善後 |
| --- | --- | --- |
| システム構成の線同士の交差（端点を除く） | 2 | 0 |
| システム構成の折れ曲がり | 12 | 9 |
| システム構成の線長合計 | 4006 | 4010 |
| アクティビティの高さ | 2276 | 1800 |
| アクティビティの線長合計 | 4996 | 4044 |
| シーケンスの配置 | 基準 | 変更なし |

小規模システムでも経路全体を比較するようにし、アクティビティの行間を調整した。同じソースを使用し、ノードや関係の削除はしていない。構成図は線長の最短化より交差の解消を優先したため、合計線長は4だけ増えている。

追加の回帰テストでは構成図の交差・共有線分・図形貫通、接続順を反転した場合の安定性、アクティビティ4方向、長い条件文と複合状態を確認。全183テストが通過。ブラウザーで3図を再描画し、警告・エラーなし、図形・文字・接続を目視確認した。

外周の経路は全てが無駄な迂回ではない。例外終了線や受付から共有データへの線は、本流を横切らないために維持している。これらの作例の改善を確認したもので、任意の入力で交差ゼロを保証するものではない。

再現用の診断と線の座標は [render-review.json](render-review.json) に保存。
